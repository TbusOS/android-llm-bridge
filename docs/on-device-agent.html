Vision · M4+愿景 · M4+

Pairing alb with an on-device agent.alb 与设备端 Agent 的协作方案。

Design note · 2026-04-21 · open for comments设计笔记 · 2026-04-21 · 欢迎讨论

This page is a design note, not a shipped feature. It describes how we want alb to evolve past the host-side agent loop — by putting a small agent on the device itself, and keeping both sides talking.这是一份设计笔记，不是已上线的功能。它描述了我们希望 alb 如何从「只在宿主侧跑 agent loop」演进到「宿主 + 设备两端 agent 协作」的路径。

Design only · no code yet只有设计 · 代码还没写 Entry points reserved已留接入口

The on-device agent is a design only; no code has been written for it yet. The current architecture reserves three entry points it can plug into later:设备端 Agent 目前只有设计，代码还没写。架构上留了三个接入口，以后从这里接进来：

  1. Bench agent operation table台架 agent 操作表
  2. Device port channel设备端口通道alb port
  3. Model backend registry模型后端注册表openai-compat takes a custom addressopenai-compat 可指定地址
The problem问题

Why host-only is not enough.为什么只靠宿主不够。

Today alb runs on Linux hosts — one machine, or a build server plus bench PCs that dial in to it. An LLM reasons on the host, pushes tool calls through adb / ssh / UART, and observes the device from the outside. This works, and the agent loop already streams, but it hits four real walls.现在 alb 跑在 Linux 宿主上 —— 可以是一台机器，也可以是编译机加上主动连回来的台架电脑。LLM 在宿主推理，通过 adb / ssh / UART 发工具调用，从外部观察设备。这套能用，对话循环也已经是流式的，但它撞了四堵墙。

Latency延迟

adb round-trips are 50–200 ms each. For a trace that walks 30 thread states, that is 3–6 seconds of pure transport — longer than the phenomenon you are trying to observe.一次 adb 往返 50–200 毫秒。看 30 条线程状态的 trace 就是 3–6 秒纯传输开销 —— 比你想观察的现象本身还长。

Blind spots盲区

Kernel panics, boot hangs, ramdump windows happen before adb exists. ANR triggers fire in milliseconds; by the time adb says “not responding”, you have lost the signal.内核 panic、启动 hang、ramdump 窗口发生在 adb 起来之前。ANR 触发是毫秒级的；等 adb 报告「not responding」时，信号已经丢了。

Cost成本

Piping long logcats to a frontier model is expensive and noisy. Most of the tokens are boilerplate the host LLM has already seen a thousand times.把长 logcat 喂给前沿大模型又贵又吵。大部分 token 是宿主 LLM 已经见过一千遍的模板文。

Autonomy离线

When the device is at a customer site with no dev reachable, nothing on the host can help. The problem reproduces, and no one is there.设备在客户现场、没有开发能接触时，宿主一切能力都白费。问题一直在复现，现场没有人。

A small agent on the device closes every one of these gaps — without replacing the host.在设备上放一个小 agent，把这四个缺口都补上 —— 而且不取代宿主。

Architecture架构

Host brain, device reflex.宿主当大脑，设备管反射。

Two cooperating agents, each doing what it is good at. A shared WebSocket keeps them in lockstep.两个协作 agent，各干各擅长的。一条共享 WebSocket 让它们保持同步。

Protocol协议

The channel.通道。

One WebSocket, six message types. alb host already speaks WebSocket (/chat/ws), so the design adds a /device/channel endpoint (proposed, not built) to the same FastAPI app and lets devices connect as clients. Authentication would reuse the shared token the bench agent already uses (ALB_AGENT_TOKEN).一条 WebSocket，六种消息类型。alb 宿主本来就已经有 WebSocket（/chat/ws），设计上给同一个 FastAPI app 加一个 /device/channel 端点（提议，尚未实现），让设备作为 client 连上来。认证沿用台架 agent 现在用的共享令牌（ALB_AGENT_TOKEN）。

Message types消息类型

device → host设备 → 宿主

HEARTBEAT

Liveness + battery + thermal + freeform health field.在线状态 + 电量 + 温度 + 自由填写的 health 字段。

device → host, unsolicited设备 → 宿主，主动推

EVENT

OOM, ANR trigger, crash, thermal warn, custom threshold. Includes a short device-side triage summary.OOM、ANR 触发、crash、thermal warn、自定义阈值。附带设备侧初筛摘要。

device → host设备 → 宿主

REQUEST

“I think this needs a bigger brain, here is what I saw.” Escalates to host LLM.「我觉得这个需要更大的脑子，这是我看到的。」升级到宿主 LLM。

host → device宿主 → 设备

RPC_CALL

“Run perfetto for 5 s on PID 1234”, “dump heap of app X”, “capture method profile”. Returns structured data.「对 PID 1234 跑 5 秒 perfetto」「dump app X 的 heap」「抓 method profile」。返回结构化数据。

device → host设备 → 宿主

RPC_REPLY

Result of an RPC_CALL, with {ok, data, error, artifacts} shape — same as the rest of alb.RPC_CALL 的结果，格式 {ok, data, error, artifacts}，和 alb 其他部分一致。

device → host设备 → 宿主

LOG_STREAM

Pre-filtered, pre-clustered logcat. Replaces the adb logcat pipe with something that has already paid its tokens for filtering.预过滤、预聚类的 logcat。替换 adb logcat 的管道 —— 过滤的 token 成本已经在源头付过了。

Offline buffering离线缓存

When the host is unreachable, the device caches EVENTs and RPC_REPLYs on disk. When the link comes back, it replays in order — with a replay_of header so the host knows the clock drift.宿主不可达时，设备把 EVENT 和 RPC_REPLY 缓到本地盘。连接恢复后按序回放 —— 带 replay_of 头，让宿主知道时钟漂移。

Plan计划

Four phases to ship.四个阶段上线。

We get value at every phase — we do not need phase 4 for phase 1 to be useful.每个阶段都有价值 —— 不用等第 4 阶段，第 1 阶段就能拿出去用。

1

Skeleton骨架

alb-mobile Android app: WebSocket client + logcat streamer + system metrics. No LLM yet. The win: replace adb logcat with a filtered, structured stream.alb-mobile 安卓 app：WebSocket client + logcat streamer + 系统指标。还没有 LLM。收益：用一条过滤过的结构化流替换 adb logcat。

2

Local brain本地大脑

Integrate AICore / Gemini Nano on Android 14+, or LiteRT + Gemma 4. Device does first-pass triage: summarize, cluster, decide whether to escalate.在 Android 14+ 集成 AICore / Gemini Nano，或 LiteRT + Gemma 4。设备做首层初筛：总结、聚类、决定要不要升级。

3

Bidirectional RPC双向 RPC

Host can dispatch device-local tools: perfetto traces, heap dumps, custom probes. No adb round-trip. Tool specs published back to host MCP automatically.宿主能调度设备本地工具：perfetto trace、heap dump、自定义探针。没有 adb 往返。tool spec 自动回传宿主 MCP。

4

Offline autonomy离线自主

Device runs standalone — captures reproducers, diagnoses locally, packages artifacts. Syncs to host when network returns. Field debugging without anyone on the other end.设备单机跑 —— 抓复现、本地诊断、打包产物。网络恢复后同步回宿主。现场调试不需要两头都有人。

Context背景

Aligned with where Android is going.和 Android 的方向一致。

Google's public direction already points here. AICore ships a system-level LLM runtime on Pixel 8+ and is expanding; Gemini Nano is the first model delivered through it. LiteRT (formerly TFLite) gives anyone a path to ship their own quantized model on-device. And Google's own “Gemma 4 for Android” push calls out the on-device agent as a flagship use case.Google 的公开方向已经指向这里。AICore 在 Pixel 8+ 上提供系统级 LLM 运行时，并在扩展；Gemini Nano 是第一个通过它交付的模型。LiteRT（原 TFLite）给任何人一条路径，把自己的量化模型带到设备端。Google 自己的「Gemma 4 for Android」也把设备端 agent 列为旗舰用例。

alb does not compete with any of that — it composes. alb-mobile will use whatever the device provides: AICore if available, LiteRT if not, Gemma 4 quantized as a fallback. The interesting work is not the model — it's the host ↔ device protocol and the division of labor. That's what we own.alb 不和这些竞争，而是把它们组合起来用。alb-mobile 有什么用什么：有 AICore 就用 AICore，没有就用 LiteRT，再退一步用量化的 Gemma 4。真正有价值的工作不是模型本身，而是宿主 ↔ 设备的协议和分工。这是我们要做的部分。

FAQ

Open questions.开放问题。

Where we do not have a final answer. Help welcome.还没定型的点。欢迎讨论。

How does alb-mobile ship — sideload or Play Store?alb-mobile 怎么分发 —— sideload 还是上 Play Store？

Developer builds will be sideload (debug APK from Releases). A Play Store track is on the table for field/autonomy use but needs review and a clear safety story.开发版走 sideload（从 Releases 下载 debug APK）。Play Store 通道在考虑中，主要针对现场 / 自主运行场景，但需要过审核，也需要讲清楚安全方案。

Is this Android-only?只支持 Android 吗？

Yes for v1. The WebSocket channel is generic; porting to HarmonyOS or embedded Linux boards (buildroot + a Gemma runner) is feasible but not on the M4 plan.v1 是的。WebSocket 通道是通用的；移植到鸿蒙或嵌入式 Linux 板子（buildroot + Gemma runner）可行，但不在 M4 计划里。

What about non-rooted devices?非 root 设备呢？

The plan assumes unrooted. perfetto, dumpsys, logcat are all available to app-level context via ADB, and AICore / LiteRT run as normal Android libraries. Some probes require adb shell escalation — those stay on the host side.方案默认非 root。perfetto、dumpsys、logcat 都对 app 层上下文开放（通过 ADB），AICore / LiteRT 就是普通 Android 库。少数探针需要 adb shell 提权 —— 那些留在宿主侧。

Security and permissions?安全和权限？

WebSocket connection uses a shared token (dev environment) or mTLS (production). Device never initiates destructive actions without a host-approved RPC_CALL. All device-local LLM inputs are logged for audit.WebSocket 连接用共享 token（开发环境）或 mTLS（生产环境）。设备不能主动做破坏性操作 —— 必须先有宿主批准的 RPC_CALL。所有设备端 LLM 输入都会记审计日志。

What about iOS?iOS 呢？

Not in scope. iOS's debugging model is fundamentally different, and Apple does not expose anything comparable to AICore or adb-equivalent at this layer. A reduced host-side alb for iOS is conceivable — not on this roadmap.不在范围内。iOS 的调试模型根本不一样，Apple 也没有 AICore / adb 的等价物。给 iOS 做一个精简版的宿主端 alb 可以想象，但不在这个路线图里。
